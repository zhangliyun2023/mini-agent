## 在本产品上的适用决定（已确认）

### 1. 自然语言求职落在第二层，终点必须是已建模的转移

用户可以用一句话表达意图，例如「看看今天有没有 HR 回我，合适的就把简历投过去」。这句话走标准第 16 节的
**第二层：需求理解与工具路由**。路由的终点只能是第一层状态契约里一条具体的、已建模的转移
（如 `deliver-resume`），再交给批准队列。

- agent 的自主权限只在「理解、拟、排」这一层。
- 「发送键永远是人点」不变。人批准的对象从「一个按钮」变成「一句话翻译出来的动作清单」。
- 自然语言不允许绕过契约直接操作页面。任何契约里没有的动作，报 `unmodeled-transition`，不执行。
- 意图路由在本仓自己实现。不接外部仓的现成件——那会把这个软件重新拴回去。

### 2. 第一层状态契约从本仓的红线表长出来

红线表是 [`contracts/red-lines.yaml`](../../contracts/red-lines.yaml)，2026-09-02 重建：
每条不可逆动作只能锚在本仓的代码或提交上。旧仓那张表里有本仓不存在的动作
（`send-resume`、`delete-online-resume`），没有抄过来——凭空抄一个 id 就等于没有锚点。

| 红线表里的字段 | 状态契约里的含义 |
|---|---|
| `approvable: true` | 可以是 `needs_approval` 转移，批准前置到点击之前 |
| `approvable: false` | 只能是 `rejected` 转移，本仓一律拦，人自己去点 |
| `implemented: false` | 前瞻建模。**不等于安全**：`start-chat` 没实现，pilot 照样误触发过 |
| 不在表里的写动作 | 可逆白名单（上传、附件入列表、在线简历保存），`allowed` |

契约必须同时记录允许、拒绝、no-op、UNKNOWN、SKIP（标准 17.4），不只列成功路径。
`test_contracts.py` 是这两者的 oracle，它同时拦「锚到外部仓」这件事。

### 3. 第一批 P0 不变量（来自已踩过的坑，即黄金回归夹具）

| 不变量 | 来源 |
|---|---|
| 同一会话最多投递一次简历；已投递不得再报「HR 未回复」 | README 2026-08-31 两处回执判定缺陷 |
| HR 未回复不得投简历 | 求职端 send pilot 硬约束 |
| 消息方向判定只能来自 uid / name 锚定，不能来自文本 | 提交 b0bbd66、0513b50 |
| 回执以当前会话容器内的页面文本为准，不以 `historyMsg` 接口为准 | README 2026-08-31 |
| 任何回执不明确的情况停下交人工，不自动重试 | README 2026-08-31 |

每条不变量至少一条外层 Given/When/Then，断言打在用户可见契约上：页面回执文本、接口返回、盘上的
outreach 记录三处对齐。

**但先分清哪些是已经在守的。** 2026-09-02 逐条对照代码，求职端 12 条不变量里 **4 条代码根本没在守**
——它们是 README 2026-08-31「初步修改方案（尚未实施）」那一节的内容，被直接写成了不变量：

| 不变量 | 代码现在实际在做的 |
|---|---|
| `receipt-scoped-to-conversation` | `geek_send.py:181` 仍读 `document.body.innerText`，侧栏污染没修 |
| `already-not-reported-as-unreplied` | 顺序相反：先判 `unable` 就 return，回执检查走不到 |
| `single-delivery-per-conversation` | 有 already 检查，但依赖上面那个不可信的判定；无 before/after 计数 |
| `approval-before-click` | 本仓没有批准队列；现在挡住误发的是 `commit=False` 默认不提交 |

所以每条不变量现在都带 `enforcement: enforced | planned`，`ensures` 只填 enforced 的，
未兑现的进 `ensures_planned`。**这个区分由测试守着，不靠自觉**——见
[`contracts/README.md`](../../contracts/README.md#契约和代码是怎么拴在一起的)。

原先这张表里还有一条「打招呼有日配额，接近上限 UI 先变黄」。2026-09-02 删掉了：它唯一的来源是
旧仓的一条 UI 规划，本仓从没实测过——三个抓取脚本都写着「不打招呼」，2026-08-29 的 pilot 记录里
也一个字没提配额。现在它是契约里的一条 `unknown` 转移（`start-chat-under-daily-quota`），
实测出上限再升回不变量。**没有锚点的规则不能待在不变量里**，那正是标准 18.1 要防的事。

### 4. 本产品不满足标准的两个前提，处理方式如下

**契约外部锚点（标准 18.1）**。求职端锚点是 `outreach.jsonl`、`_oneoff/` 日志，以及把坑写进
提交信息的那几条（2c952e3、0513b50、b0bbd66、8d24a79、c310e29）。自然语言入口的意图集合必须从
这些真实记录反推，不凭空设计。锚点必须是**本仓能验证的东西**：外部仓的常量和 plan 文档不算数，
因为它们改了本仓不会红。

**可控环境（标准 7.4）**。BOSS、腾讯校招、阿里校招都是真站点，没有测试环境，每个写动作都是真动作。
所以：

- 第一层的自动探索只覆盖读路径和批准之前的状态。
- 写路径不做序列探索。回放只用录制的 HAR + DOM 快照，不打真站点。
- 任何探索器、属性测试、BFS 序列都不得持有可写的登录态。

### 5. Trace 最低字段

每次从自然语言到页面动作的链路，共用一个 `traceId`，至少记录：意图摘要、归一后的转移 id、
命中的 skill / 工具、批准记录哈希、页面回执、盘上落点。密码、cookie、CSRF、身份证号、
完整 URL query 不进 trace（延续两份校招接力记录的安全边界）。

### 6. 报告口径

报告分开写「纯函数通过」「组件测试通过」「真实页面已运行」「真实投递已回执」，不得把前者冒充后者
（标准 17.1）。能区分：已验证、失败、未覆盖、跳过、外部依赖不可用。
