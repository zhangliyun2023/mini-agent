# 规格：mini-agent —— 从零实现的最小可用 Agent Runtime

来源：Ailoha「2026 年 Agent harness 技术笔试题」Vibe coding 部分。交付截止：2026-09-16 上午。

## 词汇表

| 术语 | 含义 |
|---|---|
| **用户 (User)** | 使用 Agent 的人，跨窗口共享长期记忆 |
| **会话 (Session)** | 用户打开的一个窗口；有独立的历史、状态袋、轮次计数 |
| **轮 (Turn)** | 一次用户输入到一次最终答案之间的全部过程 |
| **步 (Step)** | 一轮之内的一次模型决策；一步可带零个或多个工具调用 |
| **决策 (Decision)** | 模型在一步里的输出：思考 + 工具调用，或 思考 + 最终答案 |
| **工具 (Tool)** | 名称 + 描述 + 参数 Schema + 执行体；模型只看前三样 |
| **工具结果 (Tool Result)** | 工具执行输出，经**精简**后回填 context |
| **Context** | 一次模型调用实际收到的消息列表 |
| **历史 (History)** | 会话中已完成轮次的消息，已剥掉思考过程 |
| **摘要 (Summary)** | 压缩后替代老历史的一段文字 |
| **长期记忆 (Memory)** | 用户级键值对，跨会话可见 |
| **Trace** | 每次模型调用 / 工具调用 / 压缩 / 结束原因的结构化记录 |

## Problem Statement

评审方要看到一个不依赖任何 agent 框架、用真实 LLM 跑得起来的最小 Agent Runtime，并从代码与 README 判断作者是否理解：loop 的边界在哪里、模型输出如何被可靠解析、多窗口如何互不干扰、context 里该放什么不该放什么、超长时怎么压、出错时 loop 怎么不崩、过程是否可追溯。题目明确要求「注意实现细节」，并要求提交测试用例、README（运行方式 / 系统设计 / memory 召回时机与放置方式）和 AI 协作记录。

## Solution

一个 TypeScript 命令行 Agent：用户指定 `--user` 与 `--session` 进入一个窗口，输入自然语言；Agent 按「模型决策 → 执行工具 → 结果回填 → 再决策」循环，直到给出最终答案或触发安全阀。模型通过自定义三段标签协议（思考 / 工具调用 / 最终答案）输出，runtime 自行解析并容错；同一 runtime 可切换到厂商原生 function calling。会话按 (用户, 会话) 隔离并落盘，重新进入即接着聊；历史超阈值时把老轮次压成摘要；用户级长期记忆由模型显式写入、每轮整块注入。每次模型调用与工具调用都写入 JSONL trace。单元测试用脚本化假模型覆盖全部行为；集成测试用真实模型跑五个场景并把 trace 提交进仓库作为证据。

## User Stories

### 基本循环
1. 作为用户，我想问一个不需要工具的问题（如打招呼）时立刻得到回答，这样不必为简单问题等待多次模型调用。
2. 作为用户，我想让 Agent 在需要精确计算时自己决定调用计算器，这样我不必指定用哪个工具。
3. 作为用户，我想在一次提问里让 Agent 一次性完成多个工具调用（如同时查两地天气），这样不必拆成多次提问。
4. 作为用户，我想 Agent 在工具结果不够时自动继续调用，直到拿到足够信息再回答，这样多步任务不需要我逐步催。
5. 作为用户，我想 Agent 陷入循环时在有限步数内停下并把已有结果交给我，这样不会无限等待也不会白跑。

### 工具
6. 作为用户，我想用计算器算四则、括号、幂、取余，且不接受任意代码，这样安全又够用。
7. 作为用户，我想搜索（mock）返回最多三条标题加摘要，没命中时明确说没找到，这样结果可读且不撒谎。
8. 作为用户，我想在当前窗口维护一份待办（增、列、完成、删），这样能验证有状态工具。
9. 作为用户，我想让 Agent 把我的稳定信息（称呼、城市、偏好）记到长期记忆，这样下次任何窗口都记得。
10. 作为开发者，我想通过「名称 + 描述 + 参数 Schema + 执行体」注册一个新工具，不改 runtime 一行，这样加工具是配置而不是改代码。
11. 作为开发者，我想模型传错参数（缺必填、类型错、未知字段、枚举外）时工具拒绝执行并说明哪一项错，这样模型能自我纠正。
12. 作为开发者，我想工具执行抛异常时被转成带 error 标记的结果回喂模型，而不是让 loop 中断，这样一次失败不毁掉整轮。
13. 作为开发者，我想每个工具能定义自己的结果精简规则，未定义时按默认长度截断，这样长输出不会撑爆 context。

### 模型输出解析
14. 作为开发者，我想从模型输出里分别拿到思考过程、工具调用列表、最终答案，这样 runtime 能按结构决策。
15. 作为开发者，我想模型没守协议、裸文本输出时整段当最终答案，这样简单问题不会因格式失败。
16. 作为开发者，我想模型把标签写成 `<invoke>` / `<function_call>` 等常见别名时仍被识别，并在 trace 记警告，这样厂商模型的习惯差异不导致失败。
17. 作为开发者，我想模型输出的工具调用 JSON 坏掉、缺 name、或裸文本里出现像工具调用的 JSON 时，记为解析错误回喂模型重来，而不是当成答案，这样错误可自愈。
18. 作为开发者，我想模型同时输出工具调用和最终答案时以工具调用为准并记警告回喂，这样模型不会跳过工具结果乱答。
19. 作为开发者，我想同一 runtime 能一键切换到厂商原生 function calling，原生调用被转成同一套标签走同一条解析路径，这样对比两种方式只改一个开关。

### 会话
20. 作为用户，我想在窗口 1 加日历、在窗口 2 加联系人，两边的待办与对话历史互不可见，这样多任务不串。
21. 作为用户，我想关掉终端后用同一 `--user --session` 重新进入就能接着聊，这样会话不因进程结束而丢。
22. 作为用户，我想列出自己名下的所有会话，这样能找回之前的窗口。
23. 作为用户，我想别的用户看不到我的会话和长期记忆，这样数据按用户隔离。

### Context 管理
24. 作为用户，我想纯对话追问（「那北京呢」）时 Agent 记得上一轮问了什么、答了什么，这样不用重复背景。
25. 作为用户，我想带工具的追问（「把第一条标完成」）作用在上一轮建立的清单上，这样工具状态跨轮延续。
26. 作为用户，我想 Agent 不重复已经做过的工具调用，这样追问更快。
27. 作为开发者，我想同一轮内模型能看到自己刚才的思考过程，轮次结束后历史里的思考过程被剥掉、工具结果保留，这样 context 只留对后续有用的信息。
28. 作为开发者，我想历史超过条数或字符阈值时把老轮次压成一条摘要、最近几轮保留原文，切点对齐到用户消息，这样追问不断链。
29. 作为开发者，我想摘要由模型生成，模型失败时退回规则压缩（保留用户原话与答案首句），这样压缩本身不会成为故障点。
30. 作为开发者，我想单轮工具步数上限和会话历史上限都可配置，这样能按模型与成本调整。
31. 作为开发者，我想长期记忆在每轮组 context 时整块放进 system prompt 尾部，这样召回时机与位置一句话说清。

### 异常与可观测
32. 作为用户，我想模型接口超时或限流时 Agent 自动重试，仍失败则给我一条可读错误而不是崩溃，这样知道发生了什么。
33. 作为开发者，我想每次模型调用记录步号、消息条数、token、耗时、输出预览；每次工具调用记录名称、参数、成功与否、耗时、结果预览；每次压缩记录前后条数与方法；每轮记录结束原因，这样能事后复盘。
34. 作为开发者，我想 trace 按会话写成 JSONL 文件，CLI 里可实时回显，这样调试与归档用同一份数据。

### 交付
35. 作为评审，我想 clone 后复制 `.env.example`、填一个任意 OpenAI-compatible 的 key 就能跑，这样不绑定某家厂商。
36. 作为评审，我想 `npm test` 不需要 key 就全绿，`npm run test:live` 有 key 才跑真实模型，这样验证成本可选。
37. 作为评审，我想仓库里有一份真实模型运行的 trace，这样不用自己跑也能看到真实行为。
38. 作为评审，我想 README 讲清运行方式、系统设计、context 里放什么、memory 何时召回放在哪、已知取舍，这样能判断作者的理解。
39. 作为评审，我想看到 AI 协作记录：用了什么提示、真实模型暴露了什么问题、怎么解决，这样能判断作者怎么用 AI。

## Implementation Decisions

- **语言与依赖**：TypeScript + Node ≥ 20，运行时依赖只有 OpenAI SDK（当 HTTP 客户端）；测试 vitest；不引 dotenv、zod 等，参数校验与 .env 读取自写。
- **模块划分**：`llm`（接口 + OpenAI-compatible 实现 + 脚本化假模型）、`protocol`（system prompt 构建 + 输出解析）、`tools`（注册表 + 四个工具）、`session`（会话存储 + context 组装与压缩）、`memory`（用户级记忆）、`runtime`（agent 循环 + trace）、`cli`。runtime 只依赖 `LLMClient` 接口，不知道厂商。
- **输出协议**：`<think>…</think>` 可选；`<tool_call>{"name","arguments"}</tool_call>` 可多个；`<final>…</final>`。解析优先级：有工具调用则忽略 final 并记警告；无标签的裸文本当 final，但裸文本含 `{"name":…,"arguments":…}` 则记解析错误；`<invoke>` / `<function_call>` 作为别名接受并记警告。解析器永不抛异常，错误列表由 runtime 以 tool 消息回喂。
- **system prompt**：角色 + 协议说明 + 规则（精确计算必用 calculator；追问不重复调用；用户说「记住」必须调 remember，口头「记下了」不算；标签名必须是 tool_call）+ 一个 one-shot 示例 + 工具清单（含 Schema 原文）+ 长期记忆块。示例与 remember 规则来自真实模型实测偏差（见 AI-LOG）。
- **工具注册表**：`register(def)` 重名即抛；`specs()` 给 prompt；`invoke(name, args, ctx)` 顺序为 未注册检查 → Schema 校验（required、顶层类型、未知字段、enum）→ 执行 → 精简（工具自定义或默认 1500 字符截断），任何失败返回 `ok:false` 结果，不抛。`ctx` 携带 `sessionState`（有状态工具的数据袋）、`userId`、`sessionId`。
- **四个工具**：calculator（白名单字符 + `Function` 求值，非算式抛错）、search（本地语料关键词命中排序，最多 3 条）、todo（状态挂在 sessionState，add/list/done/remove）、remember（写用户级记忆）。
- **循环**：每轮 `run({userId, sessionId, input})`：取会话 → 轮次 +1 → 需要则先压缩历史 → 组 system prompt → 逐步：组 context → 调模型（带重试）→ 解析 → 无工具调用且有 final 则结束；无工具调用且无 final 则回喂解析错误继续；有工具调用则逐个执行、每个结果一条 tool 消息 → 步数到顶则以「已达上限 + 最近三条工具结果」结束。结束时把本轮消息剥掉 think 后追加进历史并保存。结束原因三种：`final` / `max_steps` / `error`。
- **Context 组装**：`[system prompt, (摘要 system 消息), …历史, …本轮消息]`。进 context 的信息：用户输入、模型的工具调用文本、精简后的工具结果、最终答案（保留 `<final>` 标签以维持协议一致性）、当轮的 think。不进的信息：历史轮的 think。
- **压缩**：触发条件为历史条数 > 40 或字符数 > 12000（可配）；保留最近 12 条，切点回退到 user 消息；老部分由模型压成 ≤200 字要点（带上此前摘要），失败退回规则压缩；摘要累积在会话上。压缩发生在新一轮开始前，只压历史不碰本轮。
- **会话存储**：接口 `get / save / list`；内存实现（测试、单进程服务）与文件实现（每会话一个 JSON，路径按用户/会话编码）。会话结构：用户、会话 id、历史、摘要、状态袋、轮次、时间戳。
- **长期记忆**：接口 `load / set`；内存与文件实现（每用户一个 JSON）。写入只经 remember 工具；召回 = 每轮组 context 时全量渲染成 `<memory>` 块放 system prompt 尾部；不做检索。
- **厂商适配**：OpenAI-compatible 客户端把 `tool` 角色消息统一降级为带前缀的 `user` 消息（厂商协议要求 tool 消息紧跟带 tool_calls 的 assistant 消息，而我们的历史是自有标签文本）；原生模式下把 `tool_calls` 转成 `<tool_call>` 标签文本再交给同一解析器。SDK 内置重试关闭，重试由 runtime 统一做（指数退避）。
- **Trace**：事件类型 llm / tool / compact / parse_error / parse_warning / stop，每条带用户、会话、轮次、时间；内存 sink（测试）与文件 sink（JSONL，按会话一个文件，可回显到 stderr）。
- **CLI**：`--user --session --native-tools --quiet`；逐行读 stdin（交互与管道都可）；`/sessions` 列会话，`/exit` 退出；数据在 `data/`，trace 在 `trace/`，均不入库。
- **配置**：`OPENAI_API_KEY` / `OPENAI_BASE_URL`（默认 DashScope）/ `MODEL`（默认 qwen3-max），从 `.env` 或环境变量读。

## Testing Decisions

- **好测试的标准**：断言只打在用户可见契约上——返回的答案文本、结束原因、会话里工具状态的可见结果、模型实际收到的 context 内容、trace 记录的事件序列。不断内部函数、不断类名、不断模型措辞。
- **主 seam（一个）**：`agent.run({userId, sessionId, input})` + 脚本化假模型。假模型按序吐预设输出，并记录每次收到的完整消息列表，因此「context 里放了什么」也从这个 seam 断言。覆盖：直接回复、单/多工具调用、步数上限、解析错误回喂、工具失败回喂、模型接口异常、两窗口隔离、纯对话追问、带工具追问、think 剥离、触发压缩（模型摘要与规则兜底）、长期记忆跨会话召回与跨用户隔离、trace 事件序列。
- **辅助 seam（两个纯函数）**：输出解析器（协议正例、裸文本、多调用、坏 JSON、缺 name、call+final 冲突、标签别名、裸 JSON、外层多套标签）；工具注册表（specs 形状、未注册、Schema 校验各分支、handler 抛错）以及四个工具各自的可见行为。
- **真实模型 seam**：同一 `agent.run`，换真实客户端，五个场景（计算、搜索 + 追问、待办跨轮 + 跨窗口、remember 跨会话、原生 function calling），无 key 自动跳过，trace 写入 `evals/live-trace/` 并提交。
- **TDD**：每个 seam 先写红测试再实现；真实模型暴露的偏差先补红测试再改解析器 / prompt。
- **先例**：作者 AI Meeting 仓库里的 vitest 单测（ragQuery / liveCoach）是同样风格。

## Out of Scope

- HTTP 服务与并发 busy 状态处理（架构题模块四用文字回答；若时间富余作为 P1 单独加）。
- 流式输出（解析器按整段工作；README 里说明取舍）。
- 向量检索式记忆、记忆自动抽取、记忆过期与冲突处理。
- 复杂压缩（分层摘要、按重要性挑选）；题目明确只要基础压缩。
- 多用户鉴权、并发写同一会话的锁。
- 真实搜索引擎、真实日历 / 联系人系统。
- 录制回放式的模型测试夹具。
