# AI 时代的软件开发：状态机测试、全链路可观测性与语义穷举

**状态**：v1 设计草案
**日期**：2026-09-01
**适用项目**：DOCX Agent Studio / Electron 桌面应用及其后端
**文档定位**：工程设计文档（同时保留个人开发心得）

## 1. 核心判断

现在大量 UI、Electron、后端和调度逻辑由 AI 生成。AI 可以很快写出“看起来合理”的代码，但它通常只验证 happy path：组件能渲染、函数能返回、按钮能点。它很难自动发现跨层的意外状态转移，例如：

- 点击登录后，错误通知却变成了另一个字段的状态；
- UI 显示“保存成功”，实际文件仍写在旧的工作空间；
- 工作空间被重命名后，定时任务仍然引用旧路径；
- 新增组件没有使用主题 token，某个主题下颜色失效；
- 菜单在常见尺寸下能显示，但被父容器、弹层或其他元素遮挡。

因此，测试不能只是“让 AI 再点几下”。需要把软件建模为**可观测状态机**：

> 每个用户事件都有允许的状态转移；每次跨层副作用都有因果链；任何意外转移都必须留下可回放的证据。

## 2. 个人心得：从登录界面开始

最初的手写矩阵以登录页为例，已经包含了几个重要维度：

- 交互对象：登录、注册、协议等控件；
- 交互状态：`hover`、点击、静止；
- API 结果：成功、失败；
- 输入状态：空白、有内容、长度边界；
- `code` 状态：空白、合法、非法、失败。

这说明做软件时真正要描述的不是一张静态页面，而是：

```text
用户动作 × 输入状态 × API 状态 × UI 状态 × 持久化结果 × 后续恢复
```

这套思路可以推广到整个桌面应用。登录只是最小、容易理解的示例；工作空间、储存位置、定时任务和复杂面板才是它在真实产品中的价值所在。

## 3. 现有能力与缺口

`mirawork-mr-submit` 已经提供了行为矩阵、正反例、邻近 invariant、真实 Electron 验证和提交前证据要求。项目中也已有：

- `plan/2026-07-06-flow-trace-findings.md`：全系统 flow trace 与问题分析；
- `plan/2026-07-05-scheduler-fanout.md`：调度器、journal、幂等和续跑设计。

它们解决的是“提交前如何证明一项改动”。本设计补充的是“AI 开发过程中如何自动探索状态空间”。当前主要缺口为：

1. 状态契约仍以 Markdown 和人工矩阵为主，未成为机器可执行模型；
2. 没有统一串起 DOM、renderer、IPC、main、API、文件、数据库和 scheduler 的 trace；
3. 没有可执行的预期状态（oracle）来判断某个变化是否允许；
4. 没有自动生成、缩减和回放失败场景；
5. 没有把主题适配、布局遮挡、重命名迁移等非功能性风险纳入同一个覆盖模型。

结论：`mirawork-mr-submit` 应继续作为交付门禁；另需一个状态探索与观测层，不能把所有职责继续堆进 checklist。

## 4. v1 目标与边界

### 4.1 目标

- 以登录界面为第一个完整示例，证明状态契约、场景生成、真实 Electron 执行、断言和回放闭环；
- 统一记录 UI → IPC → 后端 → 文件/数据库 → scheduler → UI 的因果链；
- 穷举所有**有意义且可达**的组合，而不是盲目运行无效笛卡尔积；
- 捕获主题不适配、元素遮挡、错误通知串线、路径迁移和重启恢复等问题；
- 允许单次运行约 1 小时，测试证据总量可达到 10–50 GB，但正常路径不重复保存冗余原始数据。

### 4.2 非目标

- 不承诺穷举所有可能的 CPU 调度、网络包到达时刻和无限长用户操作序列；
- 不用截图代替状态、几何和持久化断言；
- 不把生产环境的敏感数据写入 trace；
- 不用一个全局万能模拟器取代真实 Electron、真实文件系统和必要的真实后端链路。

## 5. 状态契约

每个功能提供一个机器可读的状态契约（JSON/YAML/TypeScript 均可，具体格式待实现阶段决定）。它至少描述：

```yaml
feature: login
dimensions:
  input: [empty, partial, valid, invalid, too_short, too_long, whitespace]
  interaction: [idle, hover, focused, pressed, keyboard_enter]
  api: [idle, loading, success, auth_failed, timeout, offline, server_error]
  notice: [none, account_error, password_error, code_error, network_error, success]
  window: [normal, narrow, tall_content]
constraints:
  - api=success requires input=valid
  - api=loading requires login_button=disabled
  - input!=valid implies api_request=false
transitions:
  - event: CLICK_LOGIN
    from: ready
    to: submitting
```

状态契约不记录实现细节，而记录用户可感知的状态、允许的转移和必须保持的规则。

## 6. 登录界面的语义穷举

### 6.1 需要覆盖的维度

1. 输入：为空、空格、部分输入、合法、格式错误、过短、过长、粘贴、自动填充；
2. 控件：静止、hover、focus、pressed、disabled、loading；
3. 动作：点击、Enter、重复点击、点击重试、切换密码可见性；
4. API：成功、认证失败、业务校验失败、超时、离线、服务端错误、限流；
5. 通知：无通知、字段错误、网络错误、成功通知、未知通知；
6. 生命周期：刷新、关闭、重启、后台恢复、旧请求晚于新请求返回；
7. 布局：窗口窄宽、长错误文案、主题切换、系统缩放和滚动。

### 6.2 每个场景必须有 oracle

```text
场景：密码为空，点击登录
允许：显示 PASSWORD_REQUIRED；不发 API；焦点落在密码框
禁止：进入 submitting；显示 CODE_EXPIRED；跳转首页；产生重复通知
```

```text
场景：合法输入，API 超时
允许：按钮进入 loading，超时后回到可重试状态，输入保留
禁止：显示登录成功；导航两次；无限 loading；清空所有输入
```

## 7. 组合爆炸时怎么做

“穷举”应定义为**语义穷举**，不是把所有轴直接相乘。

这里的“不是直接相乘”**不代表忽略 UI 元素**。恰恰相反：每一个可见、可点击、可聚焦、会改变布局的元素都必须进入模型。压缩的是无意义的排列，不是产品表面。

如果 AI 新增了一个没有契约的按钮、通知或菜单项，运行时元素清单与契约清单不一致时，应报告 `unmodeled-interactive-element`，而不是把它静默排除。

### 7.1 约束可达状态

先排除没有意义的组合，例如 `initial + api_success`、`button_disabled + successful navigation`。只生成状态机实际可达的状态。

### 7.2 等价类压缩

把不会改变产品语义的输入归为同一类：

- 账号长度分为 `0 / 边界下 / 合法 / 边界上 / 超限`；
- 网络延迟分为 `立即 / 正常延迟 / 接近超时 / 超时`；
- 窗口尺寸分为 `窄 / 标准 / 宽`，而不是每一个像素宽度。

### 7.3 分层覆盖

- **完整状态覆盖**：每个可达状态至少一次；
- **完整转移覆盖**：每条允许和拒绝的转移至少一次；
- **P0 组合全覆盖**：认证、保存、重命名、重启、权限、网络等高风险轴全部组合；
- **pairwise / triplewise**：对低风险维度覆盖二元或三元组合；
- **序列探索**：对重复点击、竞态和恢复路径设置最大步数，使用 BFS/DFS 和状态去重；
- **属性测试**：在完整覆盖之外生成随机长序列，失败时自动缩减为最短复现序列。

### 7.4 控制时间和外部依赖

测试环境应提供可控时钟、可控网络、可控权限和隔离文件根。定时任务不能真的等数小时；通过虚拟时钟推进触发时间，同时仍验证真实 scheduler 的状态和落盘结果。

### 7.5 允许长时间运行，但不浪费存储

1 小时 nightly/full run 是可以接受的。10–50 GB 应优先用于：失败场景完整 trace、截图/DOM 快照、磁盘快照、重放包和索引，而不是每次成功点击都保存重复的全量页面。

建议：成功路径压缩和内容寻址去重；异常路径 100% 保留；每个场景保存 `scenarioId`、模型版本、代码版本和环境指纹。

## 7A. UI 元素必须被穷举

UI 状态机需要把“空间”本身建模为状态，而不仅是按钮有没有响应：

```yaml
component: TaskCard
elements:
  - id: moreButton
    states: [hidden, visible, focused, pressed, disabled]
    onHover: visible
    layout:
      mode: overlay
      preserveCardHeight: true
      noOcclusionWith: [title, status, errorNotice]
  - id: errorNotice
    states: [hidden, visible]
    layout:
      mode: reserved-row
      maxLines: 2
```

对于“hover 后出现几个按钮”，至少要验证：

- hover、focus、键盘操作是否都能使按钮进入可用状态；
- 按钮是否真的位于最上层、可点击、可聚焦；
- 按钮出现是否改变卡片高度；如果改变，是预期的 reflow 还是错误的撑高；
- 按钮是否遮挡标题、状态、错误文案或相邻卡片。

对于“失败弹出一行字导致整个卡片变高”，不能靠测试框架猜对错，必须在契约中写清楚布局语义：

- `overlay`：错误文案覆盖在预留区域，不改变卡片高度；
- `reserved-row`：卡片预留错误行，高度变化有上限；
- `reflow`：卡片允许变高，但相邻元素必须正确下移；
- `scroll`：内容超限进入滚动区域，不得溢出或遮挡操作项。

真实运行时对每个场景采集 `DOMRect`、computed style、`z-index`、overflow、pointer-events 和可访问性树，并检查关系不变量：

```text
可见元素之间不得有未声明的重叠
可点击元素必须位于可交互的最上层
错误文案必须落在声明的容器内
预期 preserveCardHeight 时，状态切换前后高度不得变化
预期 reflow 时，相邻元素必须按规则移动且不能互相覆盖
运行时出现的交互元素必须在契约清单中
```

## 7B. 分层而不是漏测

UI 的全量测试应采用三层：

1. **组件层完整穷举**：每个组件的所有元素、局部状态、主题、内容长度和焦点路径；
2. **页面组合层**：卡片、菜单、通知、侧栏、弹层之间的遮挡、reflow 和 z-index 关系，关键交互做完整组合，低风险维度做 pairwise/triplewise；
3. **真实 Electron 层**：父组件真实装配、窗口尺寸、系统缩放、真实 IPC/API、刷新和重启。

因此，测试不会因为“元素多”而删掉元素；而是先在组件边界完整覆盖，再对页面组合做有约束的状态探索。这样既能抓到 AI 新增组件没有适配主题、菜单被遮挡、错误文案撑高卡片等问题，又不会把所有像素宽度和无限事件排列都当成独立产品场景。

## 8. 全链路埋点与状态监控

统一事件至少包含：

```ts
{
  traceId,
  scenarioId,
  step,
  event,
  source,        // user | renderer | ipc | main | api | fs | scheduler
  entityKey,
  causationId,
  requestId,
  timestamp,
  beforeState,
  afterState,
  result,
  reason
}
```

必须能回答：

- 哪个用户动作导致了这个变化？
- 哪个 IPC/API/文件操作产生了副作用？
- 这个通知对应的是哪个 requestId？
- UI 显示的状态与后端、磁盘、scheduler 是否一致？
- 这是允许的转移、失败转移，还是完全未知的转移？

测试模式记录完整 trace。生产模式只记录脱敏后的状态类别、长度区间、错误类型、路径标识摘要和 requestId；密码、token、验证码和文档内容不得进入日志。

## 9. 必须自动检查的不变量

### 通用不变量

- 未满足前置条件时，不得发起副作用请求；
- loading 状态下不能重复提交；
- 同一用户意图最多产生一个有效副作用；
- 旧请求不得覆盖新请求；
- 成功、失败、取消和超时必须是可区分的终态；
- UI、API、持久化和实际产物不能互相矛盾。

### 工作空间 / 储存位置

- UI 显示路径、持久化路径和磁盘实际路径必须一致；
- 工作空间重命名后，所有 path/cwd/目录 hash 派生状态必须迁移或明确失效；
- 刷新、重启、删除和旧会话访问必须有明确结果；
- 权限拒绝不得误报保存成功；
- 外部文件路径和复制到工作区的输入必须保持产品语义边界。

### 定时任务

- UI 显示暂停时，scheduler 不得继续触发；
- 删除成功后不得再次执行旧任务；
- 重启恢复不得重复执行已经完成的副作用；
- 任务状态、journal、持久化记录和通知必须一致；
- 过期、错过触发、网络失败和重试必须有明确原因。

## 10. UI 主题与空间布局

### 主题适配

新增组件不能只在默认主题下通过。测试应检查：

- 是否使用共享 theme token，而不是硬编码颜色；
- 所有主题下文字、背景、边框、hover、disabled、error、success 状态是否有值；
- 对比度和可读性是否满足项目标准；
- 主题切换后是否存在旧 token、透明度或 z-index 残留。

### 菜单遮挡与空间问题

菜单和弹层不能只用截图判断。需要在真实 Electron 中读取：

- `DOMRect`、computed style、`z-index`、`overflow` 和 stacking context；
- 菜单是否超出 viewport；
- 菜单是否被父容器、侧栏、对话框或其他元素遮挡；
- 目标项是否真的可点击、可聚焦、可通过键盘操作；
- 长文本、窄窗口、滚动和主题切换时是否仍然成立。

截图是辅助证据；结构化几何断言才是布局通过条件。

## 11. 建议的 v1 架构

```text
状态契约仓库
    ↓
场景生成器（约束 + 等价类 + 序列探索）
    ↓
真实 Electron 驱动器
    ↓
统一 trace 适配器
  ┌─ renderer / DOM
  ├─ IPC / main
  ├─ API / network
  ├─ filesystem / database
  └─ scheduler / journal
    ↓
状态机 oracle + invariant 检查器
    ↓
覆盖率、失败报告、最小复现和 replay 包
```

推荐把探索器命名为 `mirawork-state-explorer` 或类似名称，与 `mirawork-mr-submit` 分工：

- `state-explorer`：自动生成、执行、比较和回放；
- `mr-submit`：读取探索结果，组织真实验证证据，执行提交前门禁。

## 12. 实施顺序

### M1：登录页闭环

- 写登录状态契约；
- 接入 DOM、IPC、API trace；
- 完成 P0 状态与转移覆盖；
- 实现空提交、认证失败、超时、重复点击、Enter 提交的 oracle；
- 真实 Electron 跑通并生成可回放失败包。

### M2：主题与布局

- 加入主题矩阵；
- 加入 DOMRect / computed style 检查；
- 覆盖窄窗口、长文案、菜单遮挡和焦点可达性。

### M3：工作空间 / 储存位置

- 加入路径、cwd、重命名、权限、删除、重启和旧会话场景；
- UI、持久化、磁盘和缓存四处事实对齐；
- 专门覆盖“工作空间变化后定时任务未自动适配”的回归类别。

### M4：定时任务

- 接入 scheduler、journal、虚拟时钟和幂等键；
- 覆盖暂停、恢复、删除、错过触发、失败、重试、重启和并发；
- 检查 scheduler 状态与 UI 通知的一致性。

## 13. 验收标准

v1 只有同时满足以下条件才算完成：

- 登录页所有定义的可达状态和转移都有覆盖记录；
- 至少一个意外通知/错误状态能被 oracle 自动判定，而不是靠人工截图发现；
- 真实 Electron、IPC、API 和持久化链路均有同一 traceId 串联；
- 失败场景能自动缩减并重新回放；
- 主题和菜单布局有结构化断言，不只依赖截图；
- 工作空间重命名、刷新、重启和定时任务恢复有明确正例、反例和邻近 invariant；
- 报告能够区分：已验证、失败、未覆盖、跳过和外部依赖不可用；
- 敏感数据不会进入测试产物或生产 trace。

## 14. 真实案例：Mirawork MR !987 为什么符合这套思想

用户提供的 Mirawork MR !987 是一个很好的“状态机测试先行”案例。它不是只证明“改名按钮能点”，而是把一个真实故障拆成了可观察的状态轨迹：

```text
正常空间/原任务夹
    → 外部改名后刷新
    → 缺失态（不自动复活、不误报旧通知）
    → 历史会话再次生成
    → 按原空间/原任务夹恢复
    → 新文件落盘并可继续使用
```

这与本文的对应关系是：

| MR !987 的验收内容 | 状态机/可观测性含义 |
| --- | --- |
| `originalExists`、`movedExists`、`listedOriginal` | 文件系统事实与 UI 名册的联合状态 |
| `cwdStatus = ok / missing` | 工作空间当前状态，而不是只看展示名 |
| 刷新后不自动补回目录 | 明确的负向不变量：缺失不等于立即恢复 |
| 续聊生成后才恢复原目录和任务夹 | 受事件触发的合法迁移，而非启动副作用 |
| `oldRed / stale / relocate = false` | 禁止旧通知、旧路径状态和错误引导串线 |
| `second-*.md` 写入原任务夹 | UI、main、持久化和磁盘产物的因果闭环 |
| macOS `/private/var` 与 `/var` 兼容 | 路径归一化后的同一身份键 |
| JSON、缺失态截图、恢复态截图 | 可回放证据包，而不是口头“测过了” |
| 144 条测试、typecheck、lint、diff check、真实 Electron | 分层门禁与真实用户入口验收 |

最重要的经验有三点：

1. **正例和反例必须同时锁定。** “续聊后能恢复”只是正例；“刷新时不能自动恢复、不能出现旧红色通知”才是防止回归的反例。
2. **断言必须跨层。** 只断言 UI 文案会漏掉路径和落盘错误；只断言文件存在又可能漏掉错误通知和错误引导。需要把 DOM、IPC、main、文件系统和 scheduler 放在同一条 `traceId` 上。
3. **这是状态探索器的黄金回归夹具，但还不是通用探索器。** MR 已经手工定义了关键状态、转移和 oracle；下一步应把这些字段固化为机器可读契约，让探索器自动生成场景、检测未知转移、保存最小回放包。这样 AI 下次修改工作空间逻辑时，定时任务适配就不会依赖人工记忆。

本文采用的边界是：MR 描述和证据路径作为用户提供的案例记录；除非本地重新拉取并复跑，否则不把该 MR 的结果冒充为本次现场验证结果。

## 15. 当前判断与未决问题

### 已确定

- 工作空间储存位置和定时任务是重点扩展场景；
- 可以接受单次约 1 小时运行和较大的测试证据存储；
- `mirawork-mr-submit` 保留为交付门禁，不承担全部探索职责。

### 仍需在实现前决定

- 状态契约采用 YAML、JSON 还是 TypeScript；
- trace 是扩展已有 `flow.trace`，还是抽成独立 session protocol；
- “所有 P0 组合”的正式清单和最大序列长度；
- 生产 trace 的采样比例、保留周期和告警渠道；
- 首个工作空间重命名事故的真实复现步骤和当前代码基线。

### 证据边界

本文记录的是个人开发观察、现有项目文档、用户提供的 MR !987 案例和方法设计。当前 Mirawork 已开始实现状态契约、场景探索、oracle、trace 和布局规则的共享包，并已有包级测试；真实 Electron 全链路探索、主题矩阵、工作空间/定时任务适配仍属于后续实现与现场验证范围。因此，本文中的架构和验收标准不应被表述为整个方案已经完成或已经通过真机验证。

## 16. 修订：两层状态机的准确含义

前面把第二层写成“Agent 是否按流程完成”，还不够准确。更核心的第二层是：**AI 有没有真正理解用户需求，并选择了正确的解决路径。**

### 16.1 第一层：软件交互状态机

第一层是被开发的软件本身：

```text
用户动作 → UI 状态 → IPC/API → main/后端 → 文件/数据库/scheduler → UI 反馈
```

它检查的是软件行为：按钮是否可用、通知是否串线、菜单是否被遮挡、工作空间是否落到正确路径、定时任务是否仍引用旧位置。

### 16.2 第二层：AI 需求理解与工具路由状态机

第二层是 AI 如何接收和解决问题：

```text
用户需求
  → 需求理解与术语归一
  → 风险/边界识别
  → 匹配已有 skill、工具、项目规范和真实入口
  → 使用正确工具执行
  → 工具不适用或不存在时，快速切换到标准库/原生能力/最小自实现
  → 用与需求对应的证据验证
```

这里的关键不是“步骤越多越好”，而是**先找对已有能力，避免重复造轮子；找不到时也不能卡死，要选择最快、最可靠、可验证的替代方案。**

例如用户要做 PPT，AI 应先判断：

- 这是内容结构问题、视觉设计问题、PPTX 生成问题，还是导出后布局问题；
- 仓库是否已有 `deck-build`、模板、主题 token、渲染器和布局检查工具；
- 是否需要真实 PowerPoint/LibreOffice/渲染链路，而不是只生成 XML；
- 如果没有专用工具，是否可以用现有库和最小脚本完成，并把能力缺口标成 `UNKNOWN` 或 `SKIP`。

错误的第二层状态包括：

- 把用户要的“验证真实交互”误解成“写几个 unit test”；
- 明明有现成 skill，却自己重新发明启动脚本或测试框架；
- 工具不匹配时反复调用同一个工具，而不是切换到更快的原生能力；
- 找不到工具时假装已经完成，或把截图、静态源码和 mock 当成真实验收；
- 需求包含工作空间、主题、scheduler 等跨层约束，却只改了一个 UI 组件。

### 16.3 两层如何互相验收

| 层 | 主要 oracle | 典型失败 |
| --- | --- | --- |
| 软件交互层 | 状态转移、DOM/几何、IPC/API、文件、数据库、scheduler 一致性 | 点击 A 导致通知 B 变化；文件写到旧空间；菜单被遮挡 |
| AI 理解与路由层 | 需求覆盖、工具选择、skill 命中、替代路径、证据类型和未完成声明 | 选错工具；漏掉真实入口；只测 happy path；把未验证说成通过 |

所以一个可靠的系统必须同时回答两句话：

1. **软件有没有按契约运行？**
2. **AI 有没有理解契约，并用正确的方法证明它？**

## 17. 本次实现过程的坑与收获

### 17.1 共享包很容易制造“假完成感”

这次先实现了 `contract`、`explore`、`oracle`、`trace`、`layout` 和 `theme`。包级测试很快变绿，但它并没有自动接上真实 Electron、真实 API、文件系统或 scheduler。

收获是：报告必须分开写“纯函数通过”“组件测试通过”“真实 Electron 已运行”“packaged 已验证”，不能把前两项冒充后两项。

### 17.2 UI 元素必须有稳定身份，但不能只依赖手工标记

登录页加入了 `data-state-explorer-id`，解决了按中文文案、路径叶名和截图坐标定位不稳定的问题。随后又补了原生 `button`、`input`、`select`、`a` 的兜底采集，否则 AI 新增一个没加标记的按钮，探索器反而看不见它。

收获是：正确模型是“稳定身份 + 运行时清单 + 契约对账”，不是要求开发者为每个元素手写无限脚本。

### 17.3 结构化布局检查比截图更可靠，但第一版也会漏

`DOMRect`、包含关系、重叠和卡片高度变化可以抓住错误通知撑高、按钮遮挡等问题；但仅在元素中心调用 `elementFromPoint` 仍可能漏掉边缘遮挡、裁剪和透明覆盖层。

这提醒我：布局 oracle 也需要版本迭代，后续要加入多点采样、overflow、focus、pointer-events 和 accessibility 检查。

### 17.4 手工矩阵不能自动产生未知状态

只有“允许转移”的矩阵，BFS 只能遍历已知路径，无法凭空知道空提交、重复点击、超时和未知通知应该如何处理。后来把验证拒绝、重复提交和超时显式建模，才开始具备发现意外转移的能力。

因此，状态契约需要同时记录允许、拒绝、no-op、UNKNOWN 和 SKIP，而不是只列成功路径。

### 17.5 MR !987 把“修复”变成了可复用的证据夹具

这个案例的价值不只是 bug 已修复，而是它同时给出了：缺失态反例、恢复态正例、路径事实、通知事实、真实 Electron 证据和工程门禁。它应该被固化成黄金 replay，而不是留在一次 MR 描述里。

### 17.6 第二层必须监控“工具选择是否正确”

本次实现也暴露出一个更高层风险：如果 AI 没先找到正确的 skill、工具或项目入口，后面即使代码和测试都很整齐，也可能是在解决错误的问题。于是 Agent 的 trace 至少还要记录：

- 需求摘要和归一后的术语；
- 命中的 skill、工具和版本；
- 为什么没有使用某个更直接的已有能力；
- 工具失败后的切换路径；
- 最终证据是否真的覆盖了用户原始要求。

这就是“软件状态机”之上的“AI 解决问题状态机”。两层合起来，才是 AI 时代软件工程真正需要监控的对象。

## 18. 对“两层状态机可以无限循环”的反驳与修正版

最初的判断是：只要把软件交互状态机和 Agent 工作流状态机做好，就可以让 AI 无限循环，最终做出符合状态机的软件。这个方向成立，但表述过强，需要加入几个前提。

### 18.1 状态机不等于真实需求

状态机只能证明“软件按照我们定义的状态运行”，不能自动证明“我们定义的状态就是用户真正需要的”。

例如工作空间改名的状态可以是：

```text
原路径不存在
  → 显示 missing
  → 续聊后恢复
  → 新文件回到原任务夹
```

这条轨迹可以全部通过，但用户可能仍然不接受，因为他期望的是改名后立即迁移，或者期望定时任务也同步迁移。因此状态机必须来自外部锚点：用户需求、产品规则、真实历史缺陷和已确认的领域语义。

### 18.2 无限 loop 可能只是重复错误

如果 AI 自己写契约、自己写代码、自己写测试、自己修改失败用例，loop 可能得到“自洽但错误”的结果：

- 把错误行为写进契约；
- 删除难测场景换取绿灯；
- 只覆盖已知状态，永远不生成未知状态；
- 用 mock、截图或静态源码伪造真实证据；
- 修复 A 时破坏 B，而测试集合没有 B。

因此可靠的 loop 必须包含独立 oracle、反例生成、真实环境回放、未知状态检查和必要的人类/产品验收。不能只有“实现 → 测试 → 修复”。

### 18.3 后端可以先行，但 UI 不能最后才出现

先做后端领域状态和接口通常是正确的，但 UI 还有一组后端不会直接表达的状态：

```text
hover / focus / pressed / disabled / loading / cancel
重复点击 / stale response / 错误通知 / 长文案 / 菜单遮挡 / 主题 / 窄窗口
```

如果完全等后端完成后才做 UI，往往会发现接口缺少 `requestId`、字段级错误码、进度、取消、stale response 或恢复原因，最后仍然需要返工。

更稳妥的方式是：

1. 先建立后端领域状态和接口；
2. 同时定义 UI 投影状态和布局契约；
3. 尽早做一条真实 UI 竖切；
4. 不要求先完成完整视觉，但必须尽早验证真实交互、焦点、错误和布局。

### 18.4 两层模型还需要两个基础条件

因此完整模型不是只有两层，而是：

```text
产品需求与领域语义
        ↓
AI 需求理解与工具路由
        ↓
软件运行状态机
        ↓
Runtime Trace / UI / API / 文件 / 数据库 / scheduler
        ↓
独立 oracle、反例探索与 replay
        ↓
人类或真实用户验收
```

两层状态机是核心，但还必须补上：

- **契约外部锚点**：避免 AI 自己定义问题、自己证明问题已经解决；
- **独立证据与 oracle**：避免实现、测试和判定全部来自同一套错误假设。

### 18.5 可以接受的最终表述

在问题域有限或可分解、状态契约机器可执行、真实装配可运行、环境可回放、oracle 独立、失败可缩减，并且保留必要的人类验收时，可以让 AI 持续执行：

```text
理解需求
  → 选择已有 skill / 工具
  → 工具不可用时切换到原生能力或最小实现
  → 生成代码
  → 自动探索和反例验证
  → 最小修复
  → 回放并继续循环
```

所以修正版结论是：

> AI 时代的软件开发，可以以“需求理解与工具路由状态机 + 软件运行状态机”为核心，通过真实观测、独立 oracle、反例生成和可回放 loop，持续把软件逼近契约。后端可以先行，但 UI 状态必须并行建模，并尽早用一条真实竖切验证。

这个结论比“只要状态机做好就一定能无限循环做对”更严格，但也更可执行。
